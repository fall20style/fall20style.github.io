## HTTP/2 멀티플렉싱

HTTP/2 멀티플렉싱은 하나의 TCP 연결 안에서 여러 개의 요청과 응답을 동시에(병렬로) 주고받는 기술임.
기존 HTTP/1.1의 고질적인 문제인 HOLB(Head-of-Line Blocking, 앞선 요청이 밀리면 뒤도 다 대기하는 현상)를 해결한 핵심 기능임.

------------------------------
### 1. HTTP/1.1 vs HTTP/2 비교 (비유)

* HTTP/1.1 (1차선 도로):
* 트럭(요청) 하나가 지나가야 다음 트럭이 갈 수 있음.
   * 앞의 트럭이 고장 나거나 느리면 뒤의 모든 차가 멈춤 (HOLB 발생).
   * 해결하려고 차선(TCP 연결)을 여러 개 만들지만 자원 낭비가 심함.
* HTTP/2 멀티플렉싱 (기차/컨베이어 벨트):
* 데이터를 아주 작은 조각(Frame)으로 나눔.
   * 하나의 선로(TCP 연결) 위에 여러 요청의 조각들을 섞어서 보냄.
   * 받는 쪽에서 조각의 번호(Stream ID)를 보고 다시 조립함.
   * 하나의 요청이 늦어져도 다른 조각들은 옆으로 슉슉 지나갈 수 있음.

------------------------------
### 2. 작동 원리: 바이너리 프레이밍(Binary Framing)
HTTP/2는 텍스트가 아닌 이진 데이터(Binary)로 통신하며, 데이터를 다음과 같이 쪼개서 관리함.

   1. Frame (프레임): 통신의 최소 단위. (헤더 프레임, 데이터 프레임 등)
   2. Message (메시지): 요청이나 응답 한 세트 (여러 프레임의 집합).
   3. Stream (스트림): 하나의 연결 내에서 오가는 양방향 데이터 흐름. 각 스트림은 고유한 ID를 가짐.

------------------------------
### 3. 멀티플렉싱의 주요 효과

* 연결 효율성: 단 하나의 TCP 연결만 맺으므로 Handshake(연결 설정) 비용이 크게 줄어듦.
* 속도 향상: 이미지, CSS, JS 등 수십 개의 파일을 한꺼번에 요청해도 지연 없이 병렬 처리됨.
* 우선순위(Priority) 설정: 중요한 데이터(예: CSS) 프레임을 먼저 보내도록 우선순위를 지정할 수 있음.
* 서버 푸시(Server Push): 클라이언트가 요청하지 않아도 서버가 필요한 리소스를 미리 밀어 넣어 줄 수 있음.

------------------------------
### 4. gRPC와의 관계
gRPC가 JSON-RPC보다 압도적으로 빠른 이유 중 하나가 바로 이 HTTP/2 멀티플렉싱 덕분임.

* 수많은 마이크로서비스 간 통신 시, 매번 연결을 맺고 끊을 필요 없이 하나의 파이프로 수만 개의 RPC 호출을 동시에 처리함.



## 성능 비교

HTTP/2 멀티플렉싱과 gRPC(Protobuf) 조합이 네트워크 지연 시간(Latency)을 얼마나 줄이는지, 실제 벤치마크와 기술적 근거를 바탕으로 정리.

### 1. HTTP/1.1 vs HTTP/2 (멀티플렉싱 효과)
수십 개의 작은 자원(이미지, 스크립트 등)을 로딩할 때 차이가 극명함.

* 지연 시간 단축: 보통 30% ~ 50% 이상 감소함.
* 이유:
* TCP Handshake 제거: HTTP/1.1은 브라우저당 보통 6개의 연결을 제한적으로 생성하지만, HTTP/2는 단 1개의 연결만 유지함.
   * HOLB 제거: 앞선 요청이 서버에서 처리 지연(예: DB 조회 1초)되어도, 뒤의 요청들은 다른 스트림을 통해 즉시 응답받음.

### 2. JSON-RPC vs gRPC(Protobuf) 성능 수치
단순 전송 속도가 아니라, 데이터 직렬화/역직렬화 시간을 포함한 수치임.

* 페이로드 크기: Protobuf는 JSON 대비 약 20% ~ 40% 작음. (텍스트 필드명이 사라지고 숫자로 대체됨)
* 파싱 속도: Protobuf가 JSON보다 최대 5~10배 빠름.
* 종합 지연 시간(End-to-End Latency):
* 동일한 네트워크 환경에서 gRPC는 JSON 기반 REST/RPC보다 약 2배 ~ 3배 더 낮은 지연 시간을 기록함.
   * 특히 CPU 리소스가 제한적인 모바일 환경에서 파싱 오버헤드가 줄어들어 체감 속도가 훨씬 빠름.

### 3. 구체적 벤치마크 예시 (일반적인 마이크로서비스 환경)

| 항목 | JSON-RPC (HTTP/1.1) | gRPC (HTTP/2 + Protobuf) | 개선율 |
|---|---|---|---|
| 평균 응답 시간 | 100ms | 35ms | 약 65% 감소 |
| 초당 처리량(RPS) | 2,000 req/s | 5,500 req/s | 약 2.7배 향상 |
| 메모리 사용량 | 높음 (텍스트 파싱) | 낮음 (이진 매핑) | 효율적 |

### 4. 왜 이렇게 차이가 날까?

   1. Binary vs Text: 컴퓨터는 텍스트({ "id": 1 })를 읽는 것보다 이진수(0101...)를 메모리에 직접 꽂는 것이 훨씬 쉬움.
   2. Header Compression (HPACK): HTTP/2는 중복되는 헤더 정보를 압축하여 전송함. 매 요청마다 수백 바이트씩 차지하던 쿠키나 유저 에이전트 정보가 단 몇 바이트로 줄어듦.

### 결론
네트워크 지연 시간이 Critical(치명적)인 실시간 게임, 금융 거래, 대규모 MSA 환경에서는 gRPC 도입만으로도 인프라 비용 절감과 응답 속도 개선이라는 두 마리 토끼를 잡을 수 있음.
